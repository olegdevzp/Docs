### 6.3 "What's your experience with real-time data / WebSockets?"

**Answer:**

> I've built UIs that consume **WebSocket or SSE streams** for live data — price ticks, status updates, notifications.
>
> Key practices I follow:
> - **Single subscription per stream** with multicast operators (shareReplay, publishReplay)
> - **Unsubscribe / takeUntilDestroyed** to prevent memory leaks in long sessions
> - **Throttling UI updates** while preserving last-price accuracy
> - **Error isolation** — one stream failure shouldn't crash the whole dashboard
> - **Reconnection strategy** with backoff and user-visible connection state
>
> In trading contexts, users keep the app open all day, so memory safety and graceful degradation are non-negotiable.

### 7.4 "How do you handle conflict or disagreement?"

**Answer:**

> I assume good intent and focus on the problem, not the person.
>
> **Example:** A colleague wanted to introduce a new state management library mid-project. I disagreed because it would split patterns in our monorepo.
>
> Instead of blocking in review, I suggested a **time-boxed spike**: two days, measurable criteria (bundle size, test complexity, team familiarity). The spike showed our existing RxJS + service pattern was sufficient.
>
> We documented the decision in ADR format so future debates wouldn't reopen the same question. I committed fully to the team decision even when it wasn't my first choice.
>
> That approach — data, experiment, document, commit — works well in cross-functional, international teams where you can't always resolve things in one room.

---

### 7.5 "How do you handle tight deadlines / pressure?"

**Answer:**

> In high-pressure environments — especially anything close to trading — I prioritize by **user impact and risk**.
>
> 1. **Must be correct** (data accuracy, auth, order flow) — never compromise
> 2. **Must ship** (core user path) — negotiate scope with PM early
> 3. **Nice to have** (polish, secondary views) — defer transparently
>
> I communicate daily when pressure rises: green / yellow / red status, blockers, and options. Surprises are worse than bad news delivered early.
>
> I also protect the team from thrashing — if requirements change twice in a day, I ask for written confirmation of priority before rewriting code.

## 8. Senior-Level & Leadership Questions

### 8.1 "How do you mentor junior / mid-level developers?"

**Answer:**

> Mentoring is part of the senior role, not extra credit.
>
> My approach:
> - **Pair on hard problems** instead of taking them over
> - **Code reviews that teach** — explain why, suggest patterns, link to internal docs
> - **Graduated ownership** — start with a small module, grow to feature lead
> - **Safe failures** — I share my own mistakes in retros so juniors feel safe escalating early
>
> **Example:** A mid-level dev struggled with RxJS memory leaks. We pair-programmed once on `takeUntilDestroyed`, I added an ESLint rule for unsubscribed observables in our lib, and they became the person who reviewed streaming code for the team.

---

### 8.2 "How do you balance hands-on coding with leadership responsibilities?"

**Answer:**

> I aim for **~60–70% hands-on** as a senior IC — architecture, critical paths, reviews — and **~30–40%** on unblocking others, design discussions, and standards.
>
> I don't code every line, but I **own the hardest parts** and **set patterns** others follow. If I'm only in meetings, quality drifts; if I'm only coding, the team doesn't scale.
>
> Weekly I block focus time for deep work and keep reviews/metrics async where possible.

---

### 8.3 "How do you enforce code quality across a large team?"

**Answer:**

> Culture + automation:
> - **CI gates:** lint, unit tests, affected test runs in monorepo
> - **PR standards:** size limits, required reviewers from library owners
> - **Architectural decision records** for significant choices
> - **Shared libraries** instead of copy-paste across apps
> - **Lead by example** — my PRs follow the same rules
>
> Quality isn't policing; it's making the right thing the easy thing.

## 9. Quality, Testing & Engineering Culture

### 9.1 "What's your approach to testing?"

**Answer:**

> I treat tests as **design tools**, especially in a monorepo where regressions spread fast.
>
> - **Unit tests:** services, pipes, reducers, RxJS logic — fast feedback
> - **Component tests:** critical user flows, form validation, error states
> - **Integration tests:** API boundaries with mocked backends
> - **E2E (selective):** happy paths for trading-critical flows — not everything
>
> I practice **TDD on complex logic** (calculations, stream transformations) and at minimum require tests for bug fixes.
>
> At Tradeweb, where quality-first is explicit, I'd align with team conventions and help raise coverage on shared libraries first — highest leverage.

---

### 9.2 "What does quality code mean to you?"

**Answer:**

> Quality code is **correct, readable, testable, and maintainable by someone who didn't write it**.
>
> In a trading UI specifically: predictable performance, clear error handling, no hidden global state, and types that catch mistakes at compile time.
>
> Quality also means **operational readiness** — logging, feature flags, and the ability to diagnose production issues without guessing.

---

### 9.3 "How do you handle pressure to cut corners on quality?"

**Answer:**

> I don't say "no" blindly — I offer **options with trade-offs**.
>
> *"We can hit Friday if we ship behind a feature flag to internal users only, with automated tests on the core path. Full rollout next week after QA sign-off."*
>
> In fintech, cutting tests on order or price logic is a line I don't cross. I'd escalate if pressured, because the cost of a production bug exceeds the cost of a short delay.

### 10.2 "How do you think about UI performance for traders?"

**Answer:**

> Traders keep the app open all day with many instruments live simultaneously. Performance isn't Lighthouse scores — it's **consistent frame times under burst updates**.
>
> I focus on: efficient change detection (OnPush, signals where appropriate), virtual scrolling for large grids, minimizing template work, isolating heavy widgets, and measuring with real-world data volumes in profiling — not synthetic empty states.
>
> I also design for **degradation**: if one feed fails, the rest of the workspace stays usable.

---

### 10.3 "How do you handle sensitive financial data on the frontend?"

**Answer:**

> Frontend security basics: sanitize outputs (XSS), never store secrets in localStorage, short-lived tokens, CSP where possible, and minimal PII in client logs.
>
> I treat the UI as **untrusted** — validation on client for UX, authoritative validation on server. For display of financial data, I'm careful about rounding, locale formatting, and showing stale data indicators when streams lag.

#### Webpack performance work — deep dive

> Use this when they ask *"What webpack optimizations did you do?"* or *"How did you get 14%?"* — HR gets the short version; technical rounds get the full breakdown.

**Context**

The logistics web app ran on **Angular 17 inside an Nx monorepo**. Production builds used **Webpack 5** (via Angular/Nx build pipeline). Over time, the **initial bundle grew**: shared libs pulled charting, date utilities, and grid code into the main chunk; some feature modules were eagerly imported; duplicate packages appeared across libs after merges.

**How I diagnosed it**

1. **`webpack-bundle-analyzer`** on production stats — identified what landed in `main`, `vendor`, and lazy chunks  
2. **Angular bundle budgets** in `project.json` / `angular.json` — builds started failing warnings at ~2 MB initial  
3. **Lighthouse + WebPageTest** — TTI on dashboard route was the user-facing pain (operators open the app at shift start)  
4. **Nx dependency graph** — traced which libs dragged heavy deps into the shell app entry path  

**What I changed (webpack + architecture together)**

| Area | Problem | Fix |
|---|---|---|
| **Lazy loading** | Feature modules imported in `AppModule` / shell routes | Route-level `loadChildren` / lazy standalone routes — **webpack emits separate async chunks** per feature (shipments, vessels, reports) |
| **`splitChunks` / cache groups** | Vendor + shared code duplicated across chunks | Tuned `optimization.splitChunks.cacheGroups` — stable **vendor chunk**, shared **common chunk** for monorepo libs used by 3+ features |
| **Nx buildable libs** | Source imported from libs recompiled into app bundle bloated | Converted heavy shared UI to **buildable libraries** — precompiled outputs, cleaner graph, less repeated TS in app webpack graph |
| **Side-effect imports** | Whole libraries bundled (lodash, moment-style utils) | Replaced default imports with **path imports** / tree-shakeable alternatives; verified `sideEffects: false` in lib `package.json` where valid |
| **Dynamic import for heavy deps** | Maps / chart libs in initial path | **`import()`** for map and analytics modules — loaded only when user opens those views; webpack creates **on-demand async chunks** |
| **Duplicate packages** | Two versions of RxJS / date lib after dependency drift | **`npm dedupe` / lockfile audit** + Nx **single version policy** — one copy in vendor bundle |
| **Production webpack config** | Default config good but not tuned for our monorepo | Nx **`customWebpackConfig`** (or executor options): persistent cache for CI, `runtimeChunk: 'single'` for long-term caching, content-hash filenames |
| **Dead code** | Unused exports from shared barrel files | Stopped **barrel re-exports** that pulled entire libs; direct imports from lib entry points — better **tree shaking** |

**Example — how you explain `splitChunks` in an interview**

> *"Webpack was putting too much into the first download. I ran bundle analyzer and saw grid and chart code in `main.js` even though users land on a lighter list view first. I fixed routing so those features are lazy routes — webpack automatically creates async chunks. Then I tuned `splitChunks` so Angular, RxJS, and our shared `@company/ui` lib cache in a vendor chunk browsers reuse across deploys, while feature code stays isolated. In Nx, making the UI lib buildable stopped the app webpack graph from re-transpiling half the monorepo on every build."*
